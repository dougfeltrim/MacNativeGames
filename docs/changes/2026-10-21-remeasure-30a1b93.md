# Re-measured on the new base `30a1b93`

- Date: 2026-10-21
- Branch: `docs/remeasure-30a1b93`
- Previous: [Heat at 60 FPS](2026-10-21-heat-30fps.md)
- Status: measurements only; no code, preset or default changed in this branch

## Problem

Every number in this series was measured on `4fdda41`. The fork then synced upstream at `30a1b93`, which changed the
parts those numbers depend on: the startup shader seed is larger and is now read in place from the signed app,
`step_shader_libs` is implemented, and the pipeline archive and replay work changed how much GPU time a frame needs.
The old documents said their figures needed a fresh run; this increment makes that run and replaces the caveats with
measurements. The design, the mechanisms and the tier-1 preset did not change.

## What changed upstream

| Area | `4fdda41` (old base) | `30a1b93` (new base) |
|---|---|---|
| Seed at first start | imported into the profile (~14 s, 64,858 files) | read in place from the signed app: `发现随 App 准备的着色器 23353 个，导入 0 个文件` |
| Seed contents | 22,643 `_b.metal`, 20,572 unique, 2,071 duplicates | 23,353 files, 21,134 unique, 2,219 duplicates, 759,432,100 bytes |
| `step_shader_libs` | stub | implemented: compiles the seed and the patched variants into `build/shader-libs` with the Xcode Metal toolchain |
| Launcher and `TOTK_AUTOLOAD` | passed through | the launcher clears it, so the game always starts at the title as on the console |

Two consequences for repeating these runs:

- A scripted run that needs the save cannot go through the launcher: it starts
  `Contents/Resources/totk/build/totk-native rewritten/v0 boot` directly with the launcher's environment.
- The direct launch needs the launcher's GPU flags (`TOTK_GPU_ALLOW_SUBMIT=1`, `TOTK_GPU_WIDEN=1`,
  `TOTK_GPU_BLOCKRT=1`, `TOTK_GPU_MIDCLEAR=1`, `TOTK_GPU_BUDGET_MB=5000`). Without the first three it aborts on the
  block-compressed render-target probe.

## Benchmark fix in this series

The first new-base runs exposed a real `TOTK_BENCH` bug: `bench_collect()` advanced monotonic counters while
`tsummary()` cleared the timing rings after every 300-frame window, so a 6,000-frame request kept only 300 samples.
`538276f` copies the current window's ring before the clear. After the fix, the 900-frame check produced 900 frame,
900 GPU and 900 present samples, and the runs below produced 6,000/6,000 and 3,600/3,600. The app was rebuilt and
signed from the fixed tip (48 s) before these measurements.

## Build

First full build on the new base (work folder reused, same app location, six warm-up threads):

| Stage | Time |
|---|---|
| Seed preparation | 183 s: 23,353 variants, 13,451 startup shaders and the rest from the shared list, 23,420 translated, 67 skipped, 0 from the cache |
| Game binary and launcher | 25 s |
| Assembly, sign, macOS check, warm pre-check | ~28 s; the app folder had been checked before (`checked in 0 s`), pre-check 64/64 hits in 0.21 ms, warm step skipped |
| Total | 4 min (21:55:53 → 21:59:49) |

The per-machine warm-up step was not re-run from a cold store. The Metal store is shared by every app on the Mac,
so wiping it to reproduce the old cold path would have invalidated the other applications' caches; on the new base
the store already held the old base's libraries plus part of the new seed. The cold path's numbers stay on the
old-base page and are labeled as such.

## First launch

The store was warm from the old base when the new app first started. That is the upgrade path a player gets after a
rebuild, and it is where the new base differs most:

| Run | First frame (game time / wall) | Background warm | Pipelines | Compile calls | Store |
|---|---|---|---|---|---|
| First start after the upgrade (manual) | 4.888 s | 135.8 s | 1,213 render + 179 compute (23,353 shaders) | 23,559 source compiles, 0 precompiled | 653,110 → 668,197 KB (+14.7 MB) |
| Second start, same profile | 7.649 s | 19.7 s | 1,320 render + 179 compute | 23,355 | +0.07 MB |
| Empty profile, same store | 7.602 s / 8.08 s | 20.0 s | 1,328 render + 179 compute | 23,355, all hits | unchanged |
| Bench run, 60 FPS | 3.086 s / 3.54 s | 22.6 s | 1,328 render + 179 compute | 23,356, all hits | +389 KB |
| Bench run, 30 FPS | 3.934 s / 4.56 s | 17.2 s | 1,331 render + 179 compute | 23,355, all hits | no growth |

- The seed is read in place, so the old ~14 s import is gone. The first frame arrived 3.1–8.1 s after process start
  (game time; 3.5–8.1 s wall) across the runs, against 32.9 s wall on the old base.
- The one-time top-up is the new seed's extra variants: 1,213 render + 179 compute pipelines and 23,559 compile calls
  in 135.8 s, because the store held the old base's libraries. It ran while the game was already presenting frames,
  as the old first-launch figure did.
- Once the top-up is done, every later start warms in 17–23 s (1,320–1,331 pipelines, all hits). The old base's
  36.3 s / 182 pipelines was a smaller set: the new base builds many more render pipelines, not slower shaders.

## In-game FPS and GPU duty

Method: tier 1 (1280x720 scene, MetalFX to 1920x1080), the player's newest save (`slot_04`) loaded through
`TOTK_AUTOLOAD`, 300-frame windows, last 300 samples of each run. 60 FPS: `TOTK_BENCH=6000` (frames 301–6300).
30 FPS: `TOTK_BENCH=3600 TOTK_FPS60=0` (frames 301–3900). The load starts 15.2 s after the process does, so the first
~1,200 frames are title/load; the reported windows are in-game.

| Metric (last 300 frames) | 60 FPS (default) | 30 FPS (`TOTK_FPS60=0`) |
|---|---|---|
| Average frame time | 11.90 ms (84.0 fps rendered) | 33.31 ms (30.0 fps) |
| Frame p50 / p95 / p99 | 11.88 / 13.58 / 14.14 ms | 33.45 / 36.01 / 36.64 ms |
| Frames over 16.7 ms | 0 / 300 | 300 / 300 (the 30 FPS cadence, not a stall) |
| Game work over 33.3 ms (the frame itself, not the present wait) | 0 / 300 | 0 / 300 |
| Present rhythm | p50 16.67, max 33.33 ms; 83 repeats, 0 discards in the last 600 | p50 33.33, max 50.00 ms; 599 of 600 stopped one refresh, 0 discards |
| Displayed rate | 60.2 fps (215 frames in 3.57 s) | 30.0 fps (300 in 10.0 s) |
| GPU p50 / p95 | 10.17 / 11.12 ms | 10.02 / 10.98 ms |
| GPU work per second | ~0.85 s/s (~85% of the wall time) | ~0.30 s/s (~30%) |
| Keepalive spins per frame | 1.01 | 17.92 |
| Game work p50 / p90 / max | 12.38 / 13.07 / 15.22 ms | 12.43 / 14.57 / 17.72 ms |
| Controller interval | range 2..3, current 1 | range 2..3, current 2 |

The 60 FPS renderer runs at 84 fps and the display shows 60, so 85 of 300 rendered frames are not displayed; that is
the expected behaviour of the patch, not a dropped frame. The benchmark's "drops" column counts presents slower than
25 ms, which flags 299 of 300 frames at 30 FPS even though every one reached the screen: at 30 FPS that column is
meaningless and must not be quoted.

## GPU work per second, old base versus new base

The old heat page computed the 60 FPS duty as `GPU p50 / 16.67 ms`, which understates the load: the frame interval is
shorter than the display refresh because the renderer is uncapped. The comparable metric is the GPU work per second
of wall time, `GPU p50 × render rate`:

| Metric | Old base, 60 FPS | New base, 60 FPS | Old base, 30 FPS | New base, 30 FPS |
|---|---:|---:|---:|---:|
| Frame p50 | 14.25 ms | 11.88 ms | 33.44 ms | 33.45 ms |
| Render rate | 70.2 fps | 84.0 fps | 30.0 fps | 30.0 fps |
| GPU p50 | 12.24 ms | 10.17 ms | 11.45 ms | 10.02 ms |
| GPU work per second | 0.86 s/s | 0.85 s/s | 0.34 s/s | 0.30 s/s |

The old page's 60 FPS duty figure divided the GPU time by 16.67 ms and read 73%; the same formula on the new base
reads 61%, which still understates the load because the renderer produces 84 frames per second.

Upstream made each 60 FPS frame about 17% cheaper (14.25 → 11.88 ms p50), but the uncapped renderer spent the
headroom on more frames (70 → 84 fps), so the sustained GPU work — and therefore the heat at the default — is
unchanged at about 0.85 s of GPU work per second. At 30 FPS it fell from 0.34 to 0.30 s/s. The 30 FPS cap is still
the lever: on the new base it cuts sustained GPU work by 2.8× (was 2.5×).

## Excluded window

One 60 FPS window (frames 5101–5400) contains a 1.73 s system stall: the present rhythm reports a 1,733.23 ms
interval at frame 5,239, 319 repeated frames and 6 system discards. It is excluded; the reported 60 FPS window is
clean (0 frames over 16.7 ms, 0 discards).

## What this means for the open decision

The recommendation from [Heat at 60 FPS](2026-10-21-heat-30fps.md) stands and is stronger on the new base: on a
fanless 8 GB M1, `TOTK_FPS60=0` is the better default for long sessions, because the GPU's sustained work falls to
about 30% of the wall time. Whether to make 30 FPS the tier-1 default (and leave tier 2 at 60) is still the user's
decision; nothing is changed here.

## Trade-offs and limits

- One machine (8 GB M1, macOS 26, Command Line Tools only) and one save. The 60 FPS sampled window is ~70 s and the
  30 FPS one ~120 s; they measure a spot in the world, not a worst case.
- The cold-store build and the cold-cache warm-up were not repeated (shared Metal store); the old-base figures remain
  the reference for that path and are marked as old-base.
- The new base reads the seed in place, so the first launch no longer has the old import cost. A player upgrading
  from an old-base build pays the 135.8 s top-up once; a player installing fresh on a cold store pays the full warm
  cost, which was not measured here.
- The 25 ms "drops" column in `bench_report.py` is only meaningful near 60 FPS. At 30 FPS it flags almost every
  frame; use the game's present rhythm line instead.
