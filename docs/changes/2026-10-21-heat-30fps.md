# Heat on a fanless M1: 60 FPS versus the shipping 30 FPS cap

- Date: 2026-10-21
- Branch: `docs/heat-30fps`
- Previous: [Measured results](2026-10-21-warm-measurements.md)
- Status: measurement and recommendation; **no default changed in this branch**

## Problem

After the tier-1 preset, the game ran well on the M1 Air but the machine got hot. The Air has no fan, so sustained GPU
load turns directly into case temperature and, eventually, throttling. The question was whether the 60 FPS default was
worth its heat, or whether the game's shipping 30 FPS pacing was the better default for this class of machine.

## Why the default is 60 FPS

`games/totk/runtime/game_patches.c` patches the game's present-interval controller so that the minimum interval is 1
instead of 2 (`fps60_sites`, `fps60_enabled`). The game's speed follows the interval, so with the patch the controller can
choose 60 FPS when a frame fits, and still raises the interval to 2 or 3 on slow scenes (30 or 20 FPS) with its own
hysteresis. The patch is on unless `TOTK_FPS60=0`.

That is the right default for a Mac with thermal headroom. On a fanless 8 GB M1 it means the GPU is asked to finish a
frame every 16.7 ms for as long as the player keeps playing.

## Measurement method

- Same app, same save and spot, tier 1 (720p scene + MetalFX), warm shader store.
- Baseline: default 60 FPS patch. Comparison: `TOTK_FPS60=0`, which logs
  `60 FPS patch off (TOTK_FPS60=0): shipping present interval range 2..3`.
- The game's own 300-frame windows were used (`计时`, `帧间隔`, `上屏`, `上屏节奏`, `GPU 保活`); no new instrumentation was
  added. The numbers below are windows from the same session, not a synthetic benchmark.
- **Invalid first attempt:** the comparison run did not start because an earlier game process was still alive. The
  process is `totk-native rewritten/v0 boot`, not `MacOS/TOTK`, so a `pgrep` for the bundle name found nothing and the
  new process exited quietly. The run was only accepted after `pgrep -f totk-native` showed no process and the log
  contained a fresh startup marker. Any future heat test must check the process name, not the bundle name.

These runs were made on the original series base `4fdda41`, with the app built from it. The new base `30a1b93`
includes upstream performance work (pipeline archive, replay caches, shader prefetch), which can change how much GPU
time a frame needs. The 60 versus 30 FPS comparison and the recommendation remain the method, but the duty numbers must
be re-measured on the new base before the default is changed.

## Results

### 60 FPS (default patch)

| Window (frame) | Frame p50 / p95 | GPU p50 / p95 | Presented | GPU duty |
|---|---|---|---|---|
| 19,500 | 14.25 / 15.98 ms | 12.24 / 13.22 ms | 257 / 300 | ~73% |
| 19,800 | 14.06 / 16.25 ms | 12.10 / 13.10 ms | 254 / 300 | ~73% |
| 20,100 | 14.39 / 16.16 ms | 12.35 / 13.24 ms | 261 / 300 | ~74% |

GPU duty is `GPU p50 / 16.67 ms`. The present rhythm was 16.67 ms, with 3–4 stops longer than one refresh per 600
presents. The GPU was busy roughly three quarters of the time, and one frame in six to seven did not reach the screen
(43, 56 and 39 of 300 in the three windows).

### 30 FPS (`TOTK_FPS60=0`, shipping interval 2..3)

| Window (frame) | Frame p50 / p95 | GPU p50 / p95 | Presented | GPU duty |
|---|---|---|---|---|
| 1,500 | 33.44 / 36.31 ms | 11.45 / 12.42 ms | 300 / 300 | ~34% |

- Work time (`游戏帧工作时间`): p50 13.92, p90 15.83, max 18.16 ms over 300 frames; **zero** frames over 33.3 ms.
- Present rhythm: p50 33.33, p95 33.33 ms; 590 of 600 intervals stopped one refresh (the expected 30 FPS cadence),
  one system discard. Every frame reached the screen.
- The controller stayed at interval 2 (`区间 2..3 ... 当前 2`), so the game ran at its shipped 30 FPS pacing, not at a
  degraded 20 FPS.

### What it means for heat

At 60 FPS the GPU spends about 12.2 ms of work per 16.7 ms frame, 60 times a second: ~0.73 s of GPU work per second.
At 30 FPS it spends about 11.45 ms per 33.3 ms frame, 30 times a second: ~0.34 s per second. **The GPU's sustained work
is roughly halved**, even though each individual frame is not much cheaper — the frame is the same scene, it is just
presented half as often.

The GPU keepalive spins (short kernels that keep the GPU from downclocking) are per frame: 16.76 spin kernels/frame at
30 FPS versus 1.09–2.41 at 60 FPS in the sampled windows. Per second, 30 FPS runs half as many frames, so the keepalive
cost falls with the frame rate as well.

This matches the observed behaviour: the Air still gets warm at 30 FPS, but the sustained load that pushes it to its
thermal limit is roughly half.

## Recommendation

On a fanless 8 GB M1, `TOTK_FPS60=0` is the better default for long sessions: 30 FPS locked, no missed presents, about
half the GPU work per second. The trade-off is input latency and motion smoothness; a player who prefers 60 FPS can keep
the default.

**Open decision:** whether to make 30 FPS the tier-1 default (and leave tier 2 at 60). That would change the out-of-box
experience for every M1 Air, so it is not done here. The measurement supports it; the choice is the user's.

## Why the FPS overlay shows a different resolution

The overlay reports the **on-screen picture size** (the present viewport into the drawable), not the internal scene
resolution. With the tier-1 preset the scene renders at 1280x720, MetalFX upscales it to the 1920x1080 canvas, and the
drawable follows the window's pixel size (3338x1878 on the validation Mac). The overlay therefore reads 3338x1878 even
though the scene is 720p. This is deliberate: the number that matters to the player is what the display receives. The
internal render size is in the game log (`render resolution patch: scene render size 1280x720`).
